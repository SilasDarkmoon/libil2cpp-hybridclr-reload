## Verify 误报导致运行时崩溃（第二次崩溃修复）
- 现象：修复递归后仍在重载后崩溃，Unity 崩溃栈顶 `Object_Instantiate_TisRuntimeObject` ← `EntryWainCtrl_OpenUI` ← 异步加载链。日志末尾大量 `RepairStaleGenericInstance` 命中 `List\`1`/`ValueTuple\`2`/`Awaiter`/`UniTask\`1`/`AsyncUniTaskMethodBuilder\`1` 等**健康核心类**。
- 根因（误报）：`GenericMetadata::Inflate` 对 GENERICINST 参数每次新分配 Il2CppType（`GetInflatedGenericIntance` 里 MetadataMalloc），`current != fresh` 指针对比必然不等 → 误判 stale → 把正在被异步执行链使用的类的 methods/fields 置 NULL → 崩溃。
- 修复（重写 Verify，GenericClass.cpp）：
  1. **只校验直接 IL2CPP_TYPE_VAR 参数/返回值**：inflate 时直接返回 `type_argv[num]` 指针（attrs/byref 一致时），指针对比精确无误报；GENERICINST 等复合类型不校验（接受此限制）。
  2. **跳过不含解释器类型的实例**：`ReloadTypeReferencesInterpreter` 递归检查 def 与 type_argv（`IsInterpreterType(typeDef)` 只解码 byvalTypeIndex，不触发类解析）。
  3. 不再调 `GenericMetadata::Inflate`（消除 GetMethod→GetClass 递归路径），保留先标记防重入。
- 关键认知：`InflateGenericParameterIfNeeded` 在 attrs/byref 匹配时返回 type_argv 条目本身，否则返回 `MetadataPool::GetPooledIl2CppType` 的 interned 副本（指针对比会误报，需跳过 attrs/byref 不一致的）。
- 编译修正：`IsInterpreterType` 是 `MetadataUtil.h` 的自由函数（`hybridclr::metadata::IsInterpreterType`），不是 `MetadataModule` 成员。

## 第三次崩溃修复：restore Pass 期间禁止归一化/验证
- 崩溃栈：`RestoreCachedGenericClassesPass3` → `Class::Init` → `SetupGCDescriptor` → `GetBitmapNoInit`（Class.cpp:2105）。
- 根因：第一个程序集 restore 完成后开关已打开，**后续程序集重载的 Pass 期间** Verify/归一化仍在运行——Pass 3 `Class::Init` 触发 GetClass → Verify 把正在初始化的类的 fields/methods 置 NULL → `GetBitmapNoInit` 空指针。
- 修复：`GenericClass::BeginReloadRestore()/EndReloadRestore()` 守卫计数器，在 `Assembly::Create` 中包住 采集（CollectReusableObjects）+ InitRuntimeMetadatas + RestoreReusedClasses 全程；`NormalizeGenericInstanceArgvForReload`、CreateClass 查找归一化、`VerifyGenericInstanceMethodsFreshForReload` 在守卫期间全部静默。
- **核心教训**：重载后启用的修复代码必须同时满足 ①启动期安全 ②递归安全 ③restore Pass 期间静默。

## 第四次回归修复：Verify 重置 fields 导致 MissingFieldException（机制已订正）
- 现象：重载后 `MissingFieldException: field Singleton\`1[DialogWindowMgr]::_instance not exists`（`RaiseMissingFieldException`，hybridclr/CommonDef.h:151，由 Image.cpp GetFieldInfoFromFieldRef 按 token 迭代 `Class::GetFields` 失败抛出）。日志最后一行正是 `RepairStaleGenericInstance: klass=...(.Singleton\`1) method=get_Instance`。
- **真正机制**（用户指出 DLL 完全相同，field_count 理论不成立后查实）：各成员的懒惰重建门不同——`SetupFieldsLocked` 的门是 **`size_inited`**（Class.cpp:1091），`Class::SetupFields` 也是 `if (!klass->size_inited)` 才进（Class.cpp:1122）；而 `SetupMethodsLocked` 的门是 `if (klass->methods) return;` **按指针**。我只把 `fields=NULL` 没动 `size_inited` → fields 永不重建 → `GetFields` 首行返回 NULL → MissingFieldException。methods 置 NULL 会正常重建（实证：修复后 Awake 照常执行）。
- 修复：Verify 收敛为**只重置 methods**（恰好是正确做法）。properties/events 门是指针（理论可安全重置），但为最小化爆炸半径暂不碰。
- 遗留风险：已解决（见下）。

## Verify 改为彻底重置（用户指出 methods-only 在字段布局变化的 DLL 下会用旧字段）
- 用户质疑正确：只重置 methods 则字段保持旧布局/旧类型。修复对齐 `RestoreCachedGenericClassesPass2` 的重置集合：
  - Verify 校验范围扩大：**methods（VAR 参数/返回值）+ fields（VAR 字段类型），且 method_count/field_count 与定义不一致也判 stale（成员集/布局变化）**。
  - 修复时重置：`methods/properties/events/fields/gc_desc = NULL` + **`size_inited=0`、`size_init_pending=0`**（fields 的懒惰重建门是 size_inited 标志而非指针——这是上次 MissingFieldException 的真正原因）；**保留 static_fields 与 initialized 系列标志**（静态字段值与 cctor 状态必须存活）。
  - `SetupFields/SetupProperties/SetupEvents` 增加数量跟随赋值（`genericInstanceType->field_count = genericTypeDefinition->field_count` 等），相同 DLL 为 no-op，数量变化时让实例跟随定义，避免 GetFields 按旧上界迭代。
  - 安全性确认：`AddStaticFieldData` 只注册 GC 列表不清存储；`InitLocked` 中 SetupFieldsLocked 先于 SetupGCDescriptor；Pass 期间有 BeginReloadRestore 守卫不会触发。
- **各成员懒惰重建门（关键知识）**：methods/properties/events 按指针门（置 NULL 即重建）；fields 按 `size_inited` 门（必须同时清标志）。
